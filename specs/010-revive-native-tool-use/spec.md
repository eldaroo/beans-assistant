# Spec 010: Revive native tool-use chat (Timonel) on the Vercel/Neon stack

> Spec generated by `/create-spec` on 2026-10-26 from a 4-agent re-homing deliberation on top of spec 007's existing 6-voice design.
> Deliberation artifacts under `./.deliberation/`.

> Put the agent that understands everything back in front of the write spine. The parser was the serverless-safe stopgap; it made Timonel dumb. Revive the native tool-use loop, keep spec 009's safety kernel.

## Problem

Timonel dead-ends when it is right. On 2026-10-26 the owner typed "acaba de entrar un nuevo tipo de producto" and got "No pude interpretar eso como una operacion." The remote LLM returned `{none:true}` correctly: the phrase names an intent but no concrete op. The deeper cause is the brain. Spec 008 replaced spec 007's native tool-use agent with a propose-only parser (one pass to one of N fixed ops) because the `claude`-children loop did not port cleanly to serverless. The parser is a funnel: it dead-ends on anything outside its fixed shapes and cannot ask, reason, or understand a vague turn. Dario's call (2026-10-26): Timonel should be like Quinn-in-Discord — it understands the whole message, sees what tools it has, and acts. That is spec 007, which was built (M1-M5) and then retired. This spec brings it back, re-homed onto the Vercel/Neon stack, keeping the write-safety kernel spec 009 built.

## Why now

The owner hit the wall the same day spec 009 C3 shipped and said "sigue sin funcionar." The infrastructure to revive the agent already exists in the tree: the `beans-ai` gateway (`deploy/beans-ai.nomad.hcl`, `deploy/gateway` with `/run-agent`, the boot tool-posture self-check, the egress guard) and the beans MCP server (`deploy/beans-mcp.mjs`) with read tools AND write-preview tools already defined. What is dead is the other end of the wire: the MCP tools call a FastAPI internal API that spec 008 deleted. And spec 009 already built the write-safety substrate on the new stack (`stageOperation`, `computeVerdict`, `operator_turns` grounding, `pending_ops`, `/api/ops/confirm`, the confirm cards + auto-post + Undo). Reviving is reconnecting the box to Next and swapping the chat seam, not a rebuild.

## The binding decision

Dario chose, 2026-10-26, to run the tool-use loop on the Nomad gateway box with MCP, exactly as spec 007 did, over an Anthropic-API loop inside the Vercel route. That choice is binding. The spine is absolute and unchanged: the parser only proposes, the app re-derives the verdict, the only commit path is the non-model `/api/ops/confirm`, the model holds no DB credentials and has no commit tool. This spec swaps the brain, not the write kernel. The architecture is D-058 through D-064 in ARCHITECTURE.md (superseding D-046, the parser-as-brain); every spec-007 decision is carried forward, re-homed, or superseded per the ledger there.

## In scope

- Point the chat route at the `beans-ai` tool-use gateway (`/run-agent`), passing the operator utterance plus a server-minted turn nonce, flow nonce, and tenant out of band; keep the parser as the fallback on gateway error or timeout.
- Re-home the MCP internal operation API from the dead FastAPI to the Next.js app: read tools call the domain reads; write-preview tools call endpoints that delegate to `stageOperation`.
- A dedicated `/api/internal/ops/*` service-token route family (`INTERNAL_SERVICE_TOKEN`, constant-time compare), tenant pinned and validated against the single-business allowlist out of band, read-plus-propose only; session routes and the commit path stay `auth()`-only.
- Grounding keystone: on a write-preview tool call, the internal endpoint grounds against the server-authenticated `operator_turns` record (`groundingCorpusFor(owner, flowNonce)`), never the model's tool args, so a tool-sourced or model-invented numeral cannot auto-post.
- Two-phase writes reusing spec 009: `stageOperation` stages an `op_token` the model never sees; the route recovers staged ops from `pending_ops` by the turn nonce it minted and renders the confirm card / auto-post exactly as today; the commit stays `/api/ops/confirm`.
- The spec-007 verdict re-homed (already live in `verdict.ts`): reversible posts with a loud Undo, irreversible asks a confirm card, all server-computed.
- The spec-007 security controls on the new stack: boot tool-posture self-check with identical production argv, built-ins denied, no skip-permissions, one child per request disposed, a per-turn write cap, per-session and global tool-call caps (tighter on cancels/deactivations), a Nomad network egress firewall (deny-all except the Next internal-ops host and Anthropic), an append-only audit of every tool call and write intent, and the injection corpus re-proven.
- Live deploy: the gateway healthy, the internal API live, and the reported dead-end gone (the owner's vague message now gets a question or a proposal, never "no pude interpretar").

## Out of scope

- An Anthropic-API tool-use loop inside the Vercel route. Dario chose the Nomad box with MCP.
- New operation types beyond the existing registry menu. This revives the brain over the existing ops; it does not grow them.
- The app-side slot-filling controller (the superseded draft, D-053..D-056). A reasoner needs no slot state machine; D-064 supersedes it. D-057's multi-turn-confirm consent gate is retained.
- Multi-tenant rollout. One business, with the tenant pinned out of band as if there could be many.
- Replacing the command-center tiles or forms. The chat stays a mouth and an ear for the surface the owner already has.
- The spec-008 M8 production cutover (DNS, the client domain, retiring the old Python app), tracked separately.

## Acceptance criteria

1. `web/app/api/chat/route.ts` calls the `beans-ai` gateway `/run-agent` (passing the operator utterance, a server-minted turn nonce and flow nonce, the tenant, and a bounded history, all out of band) instead of `parseMessage`; a named test asserts the gateway path is primary and `parseMessage` is reached only on gateway error or timeout. (M1, D-058)
2. A read question ("cuanto stock me queda de X") round-trips route -> `/run-agent` -> `claude` child -> MCP read tool -> Next internal read endpoint -> domain read -> rendered answer, with the response envelope unchanged and no parser call on the happy path; verified live. (M1/M2, D-059)
3. A new `/api/internal/ops/*` route family authenticates with `INTERNAL_SERVICE_TOKEN` (`x-internal-token`, constant-time compared), not `auth()`; it reads the tenant from `x-beans-tenant` and validates it against the single-business allowlist, never from a tool arg; a token-only request returns JSON and a request without the token returns the named-error envelope. (M3, D-060, AC-T1, AC-T2)
4. The service token is read-plus-propose only: the internal routes cover reads and write-previews but never commit or undo; a named test asserts `/api/ops/confirm` and `/api/ops/undo` reject the service token and stay session-only, so the box can stage but never commit. (M3, AC-T1)
5. On a write-preview tool call, the internal endpoint builds `utterance` and `groundingCorpus` from the server-authenticated `operator_turns` record (`groundingCorpusFor(owner, flowNonce)`), never from the model's tool args; a named test asserts a model-invented numeral present in the tool args but absent from `operator_turns` fails grounding, yielding `auto:false` and a confirm card. (M3, D-061, AC-T3, AC-T4)
6. Every write-preview tool stages a validated preview and an `op_token` via `stageOperation` and commits no row; the `op_token` never crosses the gateway or the model (`callPreview` strips it); the route recovers staged ops from `pending_ops` via `verdictPendingForTurn(turnNonce)` and renders the confirm card / auto-post exactly as spec 009; the commit stays `/api/ops/confirm`; a named test drives the readback and asserts a multi-step turn renders in order. (M3/M4, D-062, D-038)
7. The reversible, grounded, obvious write ("vendi 2 medias a 300", the numerals the operator's own and the product resolving to one active candidate) is client-auto-confirmed with a loud Undo and `auto:true` set by the server; the irreversible, ambiguous, or ungrounded write shows the operator-clicked confirm card; verified live at mobile and desktop. (M4, D-040..D-044 re-homed)
8. A per-turn write cap bounds auto-post fan-out: a single grounded operator turn cannot auto-post more than the configured number of reversible writes (`numeralIsGrounded` is set-membership, not consumption); a named test drives a loop staging multiple auto-writes from one turn and asserts the cap holds. (M5, AC-T6)
9. The injection corpus is re-proven on the new stack: a read tool returns tenant-authored text instructing a write, and a named test proves no write commits (only `/api/ops/confirm` commits, non-model) and nothing auto-posts (tool output is not in `operator_turns`, so it is ungrounded); an attempt to invoke a built-in tool is denied. (M5, AC-T5, ports spec 007 AC9)
10. The Nomad gateway's network egress is firewalled deny-all except the Next internal-ops host and `api.anthropic.com`; the in-code egress guard is the second layer; a test or config asserts the firewall and a blocked egress. (M5, AC-T7, ports spec 007 AC12)
11. The gateway boot tool-posture self-check asserts, using the identical production argv, that the only allowed tools match `mcp__beans__*`, built-ins are denied, and skip-permissions is absent, exiting non-zero otherwise; one child per request is disposed after the response; a test drives the pass and the fail-closed path. (M5, AC-T8, ports spec 007 AC1-AC3)
12. Every tool call and write intent is written to an append-only audit log (name, args, caller, op_token, outcome); per-session and global tool-call caps hold, tighter on cancels and deactivations; a test drives a cap. (M5, ports spec 007 AC12)
13. The route awaits `/run-agent` synchronously with a bounded agent budget (`BEANS_AGENT_MAX_TURNS`, `BEANS_AGENT_TIMEOUT_MS`) under the route `maxDuration`, with an `AbortSignal.timeout` below it; on timeout or a model error the route falls back to `parseMessage`; the live budget is measured and set; a test drives the timeout-to-fallback path. (M3, D-063)
14. D-057's consent gate is retained: an op whose load-bearing grounding spans more than the current turn never auto-posts (`computeVerdict` forces `auto:false`), so the owner assents to the assembled whole on a final card; a named test asserts a multi-turn-assembled sale confirms rather than auto-posting. (M4, D-064)
15. The propose-only parser is retained only as the fallback, not deleted; a named test asserts the parser is reached only on gateway failure. (M6, D-058)
16. Live on prod: the `beans-ai` gateway is deployed and healthy, the Next internal-ops API is live with the service token set, a prod read matches a command-center snapshot, a confirmed sale appears in the Ventas module, and the chat answers "acaba de entrar un nuevo tipo de producto" by asking for the name and quantity (the reported dead-end is gone). (M6)

## Mockup

No new mockup. The user-facing surface is the existing Timonel chat whose shapes (answer, create card, amber confirm card, auto-post receipt with Undo) were designed and approved in spec 009's Phase 4.5 mockup and are live. - **A-Q22.** The `flowNonce` the box threads for grounding: a new MCP preview header or folded into the existing `x-beans-turn`? Default: a distinct header, since the turn and the flow have different lifetimes. Right person: Winston/Amelia at drain.
- **A-Q23.** Is the per-session tool-call cap tight enough to bound a runaway loop when the model reads a tool result then stages a write in the same turn? Default: measure, add a tool-call counter if a turn loops. Right person: Tamir/Amelia at M5.
- **A-Q24.** The service-token shape: one shared `INTERNAL_SERVICE_TOKEN` with tenant pinned and Next re-validation (the default), or per-request minting? Default: shared token now; per-request only if the callback path widens. Right person: Dario, on the operational key handling.
