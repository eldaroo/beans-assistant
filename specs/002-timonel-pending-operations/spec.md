# Timonel deferred-operation completion (pending multi-turn operations)

> Spec generated by `/create-spec` on 2026-06-14 from a 6-agent deliberation. Deliberation artifacts under `./.deliberation/`.

## Problem

When a write operation pauses to collect a missing required field, Timonel loses the operation. Real transcript Dario hit: "acabo de vender 40 stanleys" then Timonel correctly replies "Necesito el precio de venta de Termos Stanley antes de cobrar. ¿A cuánto la vendés?" (Termos Stanley has `unit_price_cents = NULL`), then the user replies "32 usd", and Timonel answers "Me falta un dato: el producto" and on the next turn loses the thread entirely. Live prod logs confirm the prior conversation IS attached to the resume turn (context length 193 on the "32 usd" turn). So this is not a memory-storage bug. Two gaps stack: the router LLM does not reliably re-extract the paused product and quantity from free-text context, and there is no pending-operation state machine, so even a correct extraction would only set the price and never complete the held 40-unit sale. The user is forced to re-state what they already said, and the original intent is silently dropped.

## Why now

Dario is recording real sales through Timonel today. The single most common real flow on a fresh catalog is "I sold N of X" where X has no price yet, which is exactly the path that loses the operation. Every paused sale that drops is either a sale the tenant never records or a sale the tenant re-enters by hand, and the assistant trains the owner to distrust it near the books. The four fixes shipped on 2026-06-14 (multi-product create, price-pending create, stable list order, login redirect) made the catalog usable; this is the next wall the owner hits the moment the catalog has price-pending products.

## In scope

- A deterministic `resume_gate` graph node that runs before the router. When a pending operation exists and the reply deterministically supplies the missing field, the gate fills the field and rebuilds the original operation in code. The router never classifies a resume turn.
- A typed `PendingOperation` record (operation type, resolved `product_id`, `quantity`, the named missing field, an `op_token`, `created_at`) persisted per phone alongside the existing in-process history store, expired by a TTL.
- Emission of the `PendingOperation` from `agents/write_agent.py` on the one pause it owns today: a REGISTER_SALE blocked because a referenced product has `unit_price_cents IS NULL`.
- A confirmation gate before any resumed financial write: the gate states product, quantity, unit price, and total and writes only on an explicit affirmative.
- Idempotent completion: an `op_token` cleared before commit and recorded with the committed sale, so a retried or double-sent turn records the sale once.
- A single active pending operation per phone. A new pause supersedes the prior one explicitly.
- TTL expiry: a pending operation older than the configured window never resumes; a later number cold-classifies.
- An explicit cancel parse that runs before field extraction: a plain-language cancel ("no, dejá", "cancelá", "olvidá") clears the pending operation and writes nothing.
- Typed-field validation: the supplied value must validate as the specific missing field; a non-price reply re-asks, never writes.
- Truthful completion copy whose figures equal the persisted row, plus one audit log line per completed resume.
- A regression suite that replays Dario's verbatim transcript and the adversarial attack cases A1 through A7.
- One generalization to a second paused operation (ADD_STOCK blocked on a missing field) through the same gate.

## Out of scope

- The conversational-memory DURABILITY rewrite of spec #63 (persistent per-tenant store, restart survival, `safe_node` fault isolation, typed error envelope). The pending record stays in-process and dies on restart by design (D-008, D-011). This spec reuses #63's ideas where they fit and does not re-spec durability.
- Any LLM-based extractor on the resume path. The match is deterministic (D-007).
- New operation types. Resume completes existing operations only.
- Resume of operations that need fresh disambiguation of more than one missing entity. v1 serves only fully-resolved-except-one-field pauses (D-012).
- Multi-worker shared state. The single-uvicorn-worker assumption is inherited from the history store and is acceptable for v1.
- Any change to the chat widget UI, channels, auth, or multi-tenant infrastructure.

## Acceptance criteria

- [ ] AC1. On a REGISTER_SALE turn where the resolved product has `unit_price_cents IS NULL`, `agents/write_agent.py` returns a state delta carrying a `pending_operation` with `operation_type="REGISTER_SALE"`, the resolved `product_id`, the parsed `quantity`, and `missing_fields=["unit_price"]`. Covered by a unit test on the pause branch.
- [ ] AC2. After a pause turn, `ChatService` holds exactly one `PendingOperation` for that phone. A second pause for the same phone supersedes the first (still exactly one). Covered by a unit test against the in-process store.
- [ ] AC3. On the next turn, when a `PendingOperation` exists and the reply validates as the missing field (a price for the sale case), the `resume_gate` node fills the field and routes into the resolver and write arm without the router classifying the turn. Covered by a graph test asserting the router classify node did not run on the resume turn.
- [ ] AC4. A resumed sale does NOT write to the database on the field-supplying turn. The gate emits a confirmation naming product, quantity, unit price, and total ("registro la venta de 40 Termos Stanley a 32, total 1280, dale?"). Zero `sales` rows exist until the user confirms. Covered by an integration test asserting zero rows after the price reply.
- [ ] AC5. An explicit affirmative on the confirmation turn ("dale", "si", "ok") records exactly one sale of the held quantity at the supplied price. A negative ("no") clears the pending operation and records nothing. Covered by an integration test that books one 40-unit sale at 32 on yes and zero on no.
- [ ] AC6. Replaying the confirmation turn (network retry, double send) records the sale once. The completion carries an `op_token`; a second completion with the same token is a no-op. Verified by a test asserting exactly one ledger row after a duplicated confirm.
- [ ] AC7. A `PendingOperation` older than the configured TTL (default 3 minutes) never resumes. A number arriving after expiry cold-classifies through the normal router path. Covered by a test injecting an expired record.
- [ ] AC8. A read-only or unrelated intent between the pause and the reply ("cuanto stock tengo") does not consume or clear the pending operation, and a bare number arriving after that non-price turn does not auto-resume without the confirmation gate. Covered by a test replaying attack A1.
- [ ] AC9. A cancel-intent reply ("no, dejá", "cancelá", "olvidá") containing no number clears the pending operation and writes nothing. The cancel parse runs before field extraction. Covered by a test replaying attack A6.
- [ ] AC10. A reply that is a number but not a valid price for the missing field ("son 40", a quantity restatement) re-asks for the price and writes nothing. Covered by a test replaying attack A7.
- [ ] AC11. The completion copy's figures equal the persisted sale row exactly (product, quantity, unit price, total), and one audit log line per completed resume names the trigger turn and those figures. Covered by a test asserting copy fields equal row fields and exactly one audit entry.
- [ ] AC12. The regression suite at `tests/integration/test_pending_operations.py` replays Dario's verbatim four-turn transcript and attack cases A1 through A7, each asserting exactly zero or one ledger row. Suite green.
- [ ] AC13. `ARCHITECTURE.md` at the repo root carries decisions D-007 through D-012 describing the pending-operation state machine, with D-001 through D-006 untouched. Covered by a grep for the decision ids.
- [ ] AC14. A second paused operation type (ADD_STOCK blocked on a missing field) resumes through the same gate and confirmation path. Covered by an integration test for a paused stock add.

## Open questions

- Q1. Idempotency storage. An `op_token` column on the `sales` row, or an in-process committed-token set keyed by phone? Right person: Winston / panel. Default the workflow proceeds with: in-process committed-token set for v1 (single worker), promoted to a column when spec #63 lands durable storage. Source: Winston A-Q3.
- Q2. Does v1 serve ADD_STOCK paused on quantity, or only sale-needs-price and product-needs-name? Right person: Dario. Default: M2 task T-011 generalizes to ADD_STOCK; M1 is sale-needs-price only. Source: Winston A-Q4.
- Q3. TTL window for a pending operation. Right person: Dario. Default: 3 minutes (Mar'ah's proposal), implemented as a dedicated `pending_ttl_seconds` so it can differ from the history `_context_ttl_seconds`.
- Q4. Does every resumed sale confirm, or only above a value threshold? Right person: Dario. Default: every resumed sale confirms in v1, because the field-supplying reply ("32 usd") is ambiguous on its face (Edut). A threshold-skip is a later refinement, not a v1 default.

## Sacred check (Section F)

This feature auto-prepares a financial write from fragmentary input, so Mar'ah's review ran as a full Legion Action Gate. Truth (Emet): completion copy must equal the persisted row (AC11). Compassion (Rachamim): the confirmation gate (AC4) and cancel path (AC9) keep the user from a surprise write. Necessity (Tzorekh): the gate writes the minimum, one sale, only on confirmation. Beauty (Tiferet): one confirmation turn is proportionate to a money write. No AC routes to `requires_human_review` beyond T-012 (live prod verification, already `human`).
